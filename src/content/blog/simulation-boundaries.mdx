这是一篇围绕 [Mcards](/projects/mcards) 技术方向整理的工程笔记。示例用于解释设计，发布日为本站整理日期，实际项目验证记录待补充。

## 先确定状态由谁修改

卡牌游戏中，一个拖放操作可能触发配方匹配、资源消耗、事件启动和界面刷新。随着功能增加，最值得先回答的问题是：谁拥有修改游戏状态的权力？

一种边界清晰的组织方式是让模拟核心独占业务状态。界面将玩家意图转换为命令，应用层决定何时提交，模拟核心完成校验和状态变化，最后发布可供表现层读取的快照。

```text
拖放交互 → 提交配方命令 → 校验条件 → 结算效果
                                         ↓
界面刷新 ← 应用层通知 ← 发布本轮状态快照
```

这一顺序的价值是把变化集中到可追踪的入口。调试某次异常时，可以先找到命令，再检查对应的前置状态、结算过程和结果。

## 用程序集表达依赖方向

目录名称能帮助阅读代码，程序集依赖则能够约束编译关系。Unity 的 Assembly Definition 可以明确程序集引用；`No Engine References` 可以关闭自动添加的引擎程序集引用。纯 C# 核心可据此建立依赖边界。[Unity Assembly definitions](https://docs.unity3d.com/2022.3/Documentation/Manual/ScriptCompilationAssemblyDefinitionFiles.html)

建议从职责而非文件数量拆分：

| 层次 | 负责的事情 | 对外提供 |
| --- | --- | --- |
| 内容 | 配方、条件、效果的定义与引用 | 已校验的内容数据 |
| 模拟 | 规则判断、状态变更与时间推进 | 命令入口和结果快照 |
| 应用 | 组织一次操作与一次更新 | 面向交互的用例 |
| 表现 | 场景、动画与界面 | 用户输入 |

先让最需要独立验证的模拟层脱离场景对象，再按实际复杂度细分其他层。边界的收益来自依赖约束与测试能力，而非程序集数量。

## 命令表达意图，快照表达结果

命令应携带稳定标识和必要参数。例如提交配方需要配方标识、参与卡牌标识，以及用于识别重复提交的请求标识。场景节点与 UI 控件属于表现层，进入核心之前应被转换为业务数据。

快照则应表达某个确定时刻的结果。以下是精简的示例类型：

```csharp
public sealed class CardSnapshot
{
    public string Id { get; }
    public string DefinitionId { get; }
    public int Energy { get; }

    public CardSnapshot(string id, string definitionId, int energy)
    {
        if (string.IsNullOrWhiteSpace(id))
            throw new ArgumentException("卡牌标识不能为空。", nameof(id));
        if (string.IsNullOrWhiteSpace(definitionId))
            throw new ArgumentException("内容标识不能为空。", nameof(definitionId));
        if (energy < 0)
            throw new ArgumentOutOfRangeException(nameof(energy));

        Id = id;
        DefinitionId = definitionId;
        Energy = energy;
    }
}
```

只读接口只是其中一层约束。即使集合暴露为 `IReadOnlyList`，底层集合仍可能被其他持有者修改。发布快照时，需要复制集合或使用持久化不可变结构，并确保元素也具有相应的不可变语义。

## 数据驱动把复杂度移到校验阶段

Recipe、Condition 和 Effect 让规则更易组合，也让内容错误更容易跨越多个文件。应当区分两类校验：

- **加载校验**：标识是否唯一、引用是否存在、参数是否满足范围约束。问题应带上内容标识和字段路径，尽早报告。
- **运行校验**：当前实体是否存在、资源是否足够、命令是否允许在这一阶段执行。结果应能被交互层解释。

对一条包含多个 Effect 的配方，还要决定失败语义。如果前两个效果已经执行，第三个效果校验失败，系统会留下什么状态？一种设计是先验证完整执行计划，再提交修改。若效果依赖逐步产生的状态，则需要明确事务、回滚或分阶段提交的规则。

## 时间顺序需要成为协议

WorldTime 和 CommandQueue 解决的不只是“什么时候执行”。同一时刻的两个操作，处理顺序可能改变结果。可以使用逻辑时刻加单调递增的入队序号进行稳定排序，并记录随机种子与内容版本。

可复现性还依赖外部输入。墙上时钟、无序容器遍历和外部回调都可能影响结果，因此重放记录需要覆盖实际影响模拟的输入。具体记录粒度应与调试需求一起设计。

## 下一步如何验证

先用小而有边界的案例验证：一个有效配方、一个失效引用、两个同刻命令、一次重复提交，以及一次跨时间节点的事件推进。每个案例记录初始状态、输入和预期结果。

随后增加不变量检查，例如资源数量满足约束、已移除实体无法继续参与结算、快照只在完整结算后发布。上述内容是一套建议验证路径，后续可以在项目页补充实际测试与重放材料。
