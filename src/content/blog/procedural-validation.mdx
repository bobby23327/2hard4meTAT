本文围绕[夜班旅馆](/projects/night-hotel)的程序化生成方向整理设计思路，代码为独立示例。发布日为本站整理日期，生成成功率与耗时需由后续实测记录提供。

## 局部连接与全局可玩性

模块接口兼容，说明相邻模块可以拼接；玩家能从入口走到指定客房，则需要检查一整条路径。这两类问题位于不同层次。

WFC 参考实现围绕候选模式、选择与约束传播展开，并可能在传播后遇到候选集合为空的矛盾。将它用于地图时，可以用相邻规则表达模块之间的兼容关系。[WaveFunctionCollapse 参考实现](https://github.com/mxgmn/WaveFunctionCollapse)

旅馆地图还需要附加玩法条件，例如所有必需客房可达、关键设施存在、门后有足够的通行空间。可以让生成器先产出候选布局，再用独立验证器判断它是否满足当前玩法要求。

## 将地图转成图

为每个可通行区域建立节点，将实际可穿行的连接建立为边。房间、走廊或更细的导航区域都可以成为节点；粒度取决于要验证的问题。

门的图边应由两个模块的接口共同决定。仅检查网格相邻会把隔墙也当作通路。单向门可以建立有向边，带钥匙的门则需要将玩家能力加入验证状态，或先验证特定阶段下可使用的边。

```text
入口 ── 大厅 ── 走廊 ── 客房 A
          │       └──── 客房 B
          └── 设施区

验证目标：从入口出发，能到达全部必需区域。
```

## 用可达集合解释失败

对于普通的无权图，可以用广度优先搜索得到入口可达的节点集合，再与必需节点集合比较。下面是精简的 C# 示例：

```csharp
public static HashSet<string> FindReachable(
    IReadOnlyDictionary<string, IReadOnlyList<string>> graph,
    string entrance)
{
    if (!graph.ContainsKey(entrance))
        throw new ArgumentException("入口必须存在于地图中。", nameof(entrance));

    var visited = new HashSet<string> { entrance };
    var pending = new Queue<string>();
    pending.Enqueue(entrance);

    while (pending.Count > 0)
    {
        var current = pending.Dequeue();
        foreach (var neighbor in graph[current])
        {
            if (!graph.ContainsKey(neighbor))
                throw new InvalidOperationException("连接引用了缺失的区域。");
            if (visited.Add(neighbor)) pending.Enqueue(neighbor);
        }
    }

    return visited;
}
```

输入图应先完成结构校验，包括节点唯一性、连接引用与接口方向。可达性检查关注入口所在的连通部分；完整结构校验还需要遍历其他区域。验证结果可记录缺失的必需节点，帮助直接定位问题区域。

## 把验证拆成独立规则

每条规则只回答一个明确的问题，并返回带上下文的诊断结果：

| 规则 | 输入 | 诊断信息 |
| --- | --- | --- |
| 接口兼容 | 相邻模块与接口描述 | 模块坐标与冲突接口 |
| 必需区域存在 | 区域类型与数量 | 缺失的区域类型 |
| 入口可达 | 通行图与入口 | 无法到达的区域标识 |
| 关键路径条件 | 图与任务节点 | 未满足的路径条件 |
| 空间可通行 | 实例化几何与角色尺寸 | 碰撞或净空问题位置 |

拓扑验证可以在实例化场景前执行，通常更便于快速定位规则问题。几何与角色通行验证则在后续阶段补足真实空间约束。最终还要通过游玩检查节奏、视觉辨识度和路径体验。

## 失败恢复要有预算

候选地图失败后，可以重试、回退或调整局部结果。选择哪种策略取决于生成算法和约束结构，但都需要设置明确的尝试次数或时间预算。预算用尽时，返回完整诊断，才能区分规则矛盾、搜索不足和配置错误。

一种值得比较的路线是先生成满足玩法的拓扑骨架，再用局部约束补充空间细节。它将关键路径提前固定，代价是减少部分拓扑自由度。实际选择应结合内容规模、失败分布和生成耗时。

## 种子只是复现记录的一部分

种子相同，模块库或算法版本变化后仍可能得到不同结果。建议一并记录生成器版本、内容版本、规则配置、随机种子、尝试次数以及失败规则。

验证阶段可以维护固定种子集与历史失败样本，每次修改约束后重新运行。新增的规则也应准备最小反例，例如一个局部拼接合法但关键客房被隔离的地图。这样更容易确认验证器检查的是正确的业务条件。

这些记录建立之后，再统计成功率与耗时分布，才能给出可解释的工程结论。
